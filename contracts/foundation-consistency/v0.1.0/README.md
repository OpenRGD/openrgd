# CORE-CAL-01C — Foundation & Runtime Validation Consistency

**2026-11-28 · candidate / non-normative / static review only.** Stacked on Core #23 exact cb23d15f8f08462aaf020d101732b9915d391115. Core standard is independent of any robot or manufacturer. The BHL genesis spec is historical reference material, not an as-built record of any robot, normative anatomy, required actuator catalog or source of physical authority. Paky-01 and Paky-02 are downstream instances. Do not encode any instance ID, body dimensions, motor list, sensor list or robot-specific alias in the Core rules.

## Decisions

1. Keep identity namespaces explicit: nominal link/joint, actuator instance, reusable component model, sensor, driver, control profile and QoS are different objects. A name match across namespaces is not a binding. An unresolved symbol means insufficient or inconsistent data, not evidence of missing physical equipment. No guessed aliases, auto-creation, motor substitution or numerical parameter fill. Coupling, passive joints, non-kinematic actuators and changing AsBuilt revisions need explicit future contracts; no one-joint/one-motor or humanoid assumption.
2. Use the existing externally selected 01B profile, never auto-require all Foundation or Operation documents. OPTIONAL absent remains admissible if unreferenced; NOT_APPLICABLE is an explicit exclusion, not an error waiver. Unclassified present or applicable unresolved references fail. A virtual/no-actuation scope can omit physical modules; a manipulator or wheeled mechanism can use different identifiers. The v0.2.0 legacy document shapes still constrain this prototype; no claim of full support for every robot type.
3. Keep the existing exact 01A/01B algorithms and reports. 01C groups *all* non-resolved reference occurrences by typed rule, status and target, preserving source pointers, and retains the full prior report. Groups are review tasks, not inferred unique physical defects or suggested substitutions. New code is generic across IDs. No alternate hash or second inventory.
4. **Declared failure-policy review** (proposed semantics, not an accepted runtime gate): examine a preflight declaration's exact local block_motion_bool and global severity allow_motion_bool. If either demands blocking, the conservative static projection is BLOCK_REQUIRED **if that check fails**. When global disallows but local does not block, record conflict, require owner review; do not let local override global. Local block with global allow is stricter, not a contradiction under this candidate. Both nonblocking => NO_BLOCK_FROM_THIS_RULE, never ALLOW or permission. Missing/ambiguous/malformed declarations => INDETERMINATE or blocked assessment; no positive default. Runtime evidence, severity and policy selection, latch/acknowledge/recovery, action classes, independent safety and reflex remain their owners' responsibilities. No real preflight was executed; this rule never issues a stop, starts motion or decides hardware state. Continuous monitor and full safety_critical semantics remain outside this scope.
5. **Description commitments:** legacy target_description_hash_str does not identify a digest profile. Keep LEGACY_UNQUALIFIED by default, even if bytes happen to match. The known empty-string SHA-256 is a placeholder in this scoped review, not evidence of a physical binding. Under explicit external RAW_DESCRIPTION_SHA256_V0.1_CANDIDATE selection only, compare exact raw indexed description bytes from the same stable snapshot. MATCH means equality to that candidate byte commitment, not source-tree identity, model equivalence, trusted issuer, applicable CAL profile or physical calibration. No automatic rewrite, reseal, conversion of model_sha256, or assignment of a digest to old measurements. The owner must review and adopt explicit digest semantics and new revision before migration. Future digest profiles need versioned adapters, not inference from hash syntax.

Use the reviewed checkout and 01A/01B dependencies. `review_consistency(bundle, profile_raw, description_digest_profile="LEGACY_UNQUALIFIED")` returns the closed candidate report. CLI:
```bash
PYTHONPATH=src python contracts/foundation-consistency/v0.1.0/consistency.py --bundle /path/to/project --profile /path/to/reviewed-profile.json
```
Optional `--description-digest-profile RAW_DESCRIPTION_SHA256_V0.1_CANDIDATE` selects the experimental exact raw comparison; never select it from the source manifest. Exit 0 only for SCOPED_CLEAR, 2 for review required, blocked or rejected input. Not a universal conformance claim or an execution gate. Report contains previous 01B report and digest (existing local serialization), scoped runtime rows and description comparison. Known findings remain visible, no normalization to a green result. No time, build or source provenance proof. As in 01A/B, stable trusted input and interpreter/private temporary storage assumed. The original is copied once; nested 01B/01A private copies are bounded by existing limits; 01C binds the exact files it uses to returned raw commitments before evaluating. No network, hardware, source mutation or external schema resolution.
