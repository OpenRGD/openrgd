## Ownership and threat model

A module namespace is a delegated publishing scope, not a DNS ownership proof, robot/Life identity or device permission. The official catalog remains rgd-modules; Core defines candidate evidence semantics. Proposed TUF profile: independently provisioned trusted root, separate root/timestamp/snapshot/registry-targets roles, direct terminating publisher delegation scoped to its namespace. Producer controls proposal target only; registry controls separate review target. No top-level shortcut for publisher role; reject overlapping selected delegations or shared publisher/registry keys. Exact proposal bytes and exact inspection report digest are bound by review target. Source and build provenance are separate from TUF delegation. TUF client verification must use a protected persistent cache and real trusted time; no acceptance after a failed refresh, no bootstrap reset on retry. Target existence alone is not sufficient to activate code.

Use Python-TUF's supported client workflow rather than custom signature or update logic. Consult [TUF specification](https://theupdateframework.github.io/specification/latest/) and [python-tuf](https://github.com/theupdateframework/python-tuf). A real registry requires separately reviewed trust root custody, thresholds and delegation policy, protected state/clock, rotation/revocation and authenticated snapshot hosting. Do not publish test keys. Registry-side candidate will exercise actual TUF metadata verification and refresh using generated test keys and synthetic transport. This Core package itself contains no keys or signature verifier.

TUF metadata version/freshness protection is distinct from **immutable release identity**. A registry may legitimately publish new metadata versions, but cannot overwrite an admitted module_id/version with different bytes. Require a durable, transactional release-key ledger including withdrawal/revocation tombstones, scoped by catalog. Until implemented, offline review compares an independently supplied prior commitment and rejects mismatch; absence in a local view is not global uniqueness or a durable commit. A legacy v0.1 key is incomparable and must be rejected by the existing registry review bridge. Do not use a new key to repair an ambiguous publication.

## Restricted artifact profile

This is a first actual inspection path, not a universal wheel verifier or package installer:
- one pure Python wheel, one facade binding, exact py3-none-any tag and no build tag; one import root, package-relative module.openrgd.json and descriptor bytes, legacy openrgd_commands/<entry-point>.json layout; one rgd.commands entry point matching the original descriptor, no extra entry-point group;
- maximum 1 MiB compressed bytes per existing proposal, 256 regular entries and 4 MiB expanded bytes; no extraction, symlinks, encrypted entries, path aliases, duplicate casefold paths, .data spread scheme, .pth, native binaries or deprecated embedded signatures; bounded ZIP read and CRC;
- verify filename, declared package-native version/name using Python packaging semantics (no change to OpenRGD release version), dist-info METADATA/WHEEL, actual RECORD coverage, exact SHA-256 and sizes for every entry except RECORD itself, exact embedded manifest/descriptors and facade declaration. Source code is not imported. A syntactically present module is not proof that its hook exists or is safe.
- The successful report means only this restricted format and commitment check passed. It does not certify package contents, dependency policy, sandboxing, build/source provenance, runtime compatibility, permissions or actual installation. No inference from a signed claim alone.

The [PyPA wheel specification](https://packaging.python.org/en/latest/specifications/binary-distribution-format/) is the reference; this profile is deliberately stricter than the general format. Native executable/library, OCI, firmware, data and model profiles require separate format, platform and provenance verifiers. All other profiles fail closed here. Actual source and builder verification (e.g. in-toto/SLSA provenance binding exact subject digest, source revision and trusted builder) remains separate; see [SLSA provenance](https://slsa.dev/spec/v1.1/provenance). A Git commit string and a signer of a proposal do not prove a build came from that revision.

## Evidence and review target

WheelInspection binds the earlier exact proposal bytes and actual artifact digest/size, filename, restricted format checks and negative authority flags. RegistryReviewTarget binds the report digest and exact proposal digest, delegated namespace and REVIEWED_CANDIDATE or WITHDRAWN. Both are closed candidate schemas; a JSON record by itself proves nothing. The target's digest is computed with the existing local deterministic encode_proposal format, not a new signature/canonical JSON profile. Actual TUF target metadata signs the byte digest; the consumer must independently repeat inspection and compare. No separate editable manifest, release index or registry entry is created.
