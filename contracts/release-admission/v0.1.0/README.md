## Registry versus Manager

Registry: independent review/authentication; trusted writer and policy; immutable key and disposition; generated snapshot; independently authorize/sign exact catalog target; retain complete source, build and review evidence in controlled archive. Manager: independently provisioned catalog root and scope, refresh TUF metadata, check exact target bytes and schema, select exact release key, reject nonselectable/unsupported entries, check artifact digest/size; later resolve dependency graph and lock, local host compatibility, staged install, configuration, lifecycle and least privilege. Console/CLI/OS reuse that manager, no direct ledger DB or publisher/build validation. No manager action may be granted by a catalog entry. A candidate preview has installable=false even when authenticated.

The reference Registry adapter reads a single SQLite snapshot using existing audit and transaction; ledger is a TRUSTED private owner input, not an untrusted proof. A context string or hash chain alone does not establish authentic review. Only approved writer/authorizer and independent registry signing process may use this projection. The producer cannot sign the catalog through a delegated proposal role. Test fixtures use separate ephemeral TUF roles and a real provenance-checked candidate ledger. Core validates record relationships, not TUF cryptography. `admission.py` is the registry-side projection; `catalog_contract.py` is the shared read-only wire/consumer helper and does not import build-provenance or wheel-inspection code. The consumer adapter uses real TUF Updater and exact direct top-level targets entry. No artifact fetch, install, import, start, or network API in this wave.

Catalog binds catalog_id, ledger_id, full checkpoint and exact sorted entries. Keep immutable admission bytes and disposition tombstones even if withdrawn/revoked. Current state is as of authenticated snapshot, NOT real-time revocation; reject removed or changed previously retained keys, stale checkpoint or terminal reversal when supplied a trusted previous authenticated view. This local comparison does not prove extension of ledger hash chain; storage, policy and signer remain trusted. TUF persistent cache prevents metadata rollback under existing protected-cache/clock assumptions. Caller must retain the last authenticated view independently; no crash-atomic cache+view storage or production checkpoint service. No reset on failure, no automatic fallback or shutdown. One catalog/lineage, max 16 entries and prior bounded JSON parser; no auto-pruning or pagination. No requirement for a robot-specific implementation, host or UI.

## Gate before actual admission

This is a prototype of an authenticated review projection and manager boundary, **not** actual Verified Release Admission for production. All publication_committed/installable/grants_authority flags false. Actual admission needs explicit independent release approval bound to current policy and verified provenance, durable state distinct from reservation, atomic release/withdrawal/outbox and signed snapshot reconciliation, protected trust/cache and archive, full builder and dependency policy, production key custody and independent test/consumer acceptance. A previously signed preview is not current eligibility after an authenticated newer disposition. No source model digest or physical binding inference. EXT-01C can start with read-only planning contracts; installing a new release remains gated.

No change to prior Core/Registry sources, catalog, spec, seed, runtime, CAL branches or hardware. Scope remains a reusable protocol independent of BHL, Paky-01 or RGD-OS implementation.
