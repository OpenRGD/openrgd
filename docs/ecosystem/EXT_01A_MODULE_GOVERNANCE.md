# EXT-01A — Module authority and terminology decision record

**2026-11-26 · proposed for maintainer acceptance · candidate, non-normative.**
Companion to Core PR #18. This proposal fixes engineering direction, not the accepted standard. See existing GOVERNANCE.md: changes of ownership or accepted contracts require explicit maintainer decision, compatibility and conformance.

## Decisions

- EXT-D01 — `OpenRGD/rgd-modules` is the sole official OpenRGD **release catalog**. Core `openrgd` owns common semantic and interface definitions. Core's future ecosystem inventory links to the catalog and RI evidence, never creates an independently editable install list. Do not activate the reserved rgd-core repository. A standard should allow other catalog implementations, private scoped catalogs and publisher namespaces; a consumer selects explicitly trusted catalogs. Namespace delegation and revocation are externally verified, not granted by reverse-domain strings. No global monopoly, assumed domain ownership, or automatic last-wins merging. Collisions between trusted catalogs are explicit conflicts until resolved by policy.
- EXT-D02 — Single authoring per datum. The producer's versioned manifest is authoritative for declarations. The registry release owns reviewed publication, exact producer manifest digest, source/artifact identity and catalog status metadata. Generate descriptor/index projections from verified inputs; do not manually duplicate declarations in Console, OS or Core. A catalog publication is a separate approval, not automatic from a producer commit. Do not allow the manifest to self-approve or embed its own final Git commit/hash recursively.
- EXT-D03 — Different identities. Adopt the glossary and machine-readable vocabulary fragments under contracts/module-vocabulary/v0.1.0. Separate module, release, artifact, extension, instance, capability, port, contract, composition and host. Functional roles are discovery tags; artifact and execution labels are independent. No category, language, role or version implies authority. Do not use `module_id` as robot identity, Life or a host resource ID.
- EXT-D04 — Independent versions. Canonical standard, toolchain, extension/manifest/interface/registry protocols, module releases, native package versions, immutable artifact digests and catalog snapshots are independent. Published release keys are immutable, no overwrite or implicit floating main. Preview may use prereleases; the candidate version profile excludes SemVer build metadata in release keys to avoid ambiguous identity (artifact variants carry separate IDs). Package-native version strings are preserved, mapped only explicitly. Contract maturity uses existing Core governance; publication state/channel, compatibility and host state are independent.
- EXT-D05 — Trust and lifecycle. Discovery parses bounded metadata without importing code. Review/enable/activation/installation and effect authorization are different scopes. A declaration may request permission, never grant it. No automatic activation, upgrade, device access, shell execution or arbitrary frontend code from a descriptor. Local manager resolves exact lock and approved operations. PERIPH owns devices and leases; Somatic retains independent safety/reflex. Core-B effect gates and Core-C Life binding remain externally verified. Catalog withdrawal/revocation is not a raw motor stop instruction; handle active critical runtime using its independent safety procedure. Unknown trust/unsupported kind fails closed for new privileged operations, while offline diagnostic/recovery remains usable.
- EXT-D06 — RGD-OS consumes the same catalog and host manager protocol as Console/CLI, without requiring the GUI. Initially composition atop Linux and reviewed supervisors, not a new kernel claim. One generic backend per supported distribution/activation profile, not one route/installer per module. Keep dataflow, dependency resolution, startup and authority independent; runtime feedback cycles are normal. Separate source and artifact verification from operational testing. Do not freeze RPC transport, container orchestrator or privileged runtime ABI before evidence.

## External references and specification discipline (informative)

- [BCP 14, RFC 2119 / RFC 8174](https://www.rfc-editor.org/info/bcp14/): reserve uppercase requirements terminology for formally adopted requirements and explicitly specify scope. This proposed decision does not adopt a normative requirement by spelling MUST.
- [SemVer 2.0.0](https://semver.org/spec/v2.0.0.html): declared public API, immutable released version, semantic compatibility. Our initial release-key subset excludes build metadata, not a universal replacement for package managers.
- [PyPA version specifiers](https://packaging.python.org/en/latest/specifications/version-specifiers/): exact package-native versions and explicit mapping to a module release.
- [OCI Image Spec v1.1.1 descriptor](https://github.com/opencontainers/image-spec/blob/v1.1.1/descriptor.md): digest, media type and size for content; evaluate OCI transport/artifacts without requiring containers for all modules.
- [The Update Framework specification 1.0.37](https://theupdateframework.github.io/specification/v1.0.37/): evaluate authenticated snapshots, delegated trust, rollback/freeze protection and expiry rather than inventing signature/update protocols. No claim of TUF integration.
- JSON Schema Draft 2020-12: offline validation, explicit local schema references and positive/negative conformance; schema validity is not provenance, permission or proof of operation.
